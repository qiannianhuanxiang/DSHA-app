## 应急工具派发兼容修复

完整软件回归实际发现：公共 [授权策略](../../app/src/main/assets/destructive-policy/index.js) 已传入 expectedConnectionPort，而 [应急 SDK](../../app/src/main/assets/recovery-native-consent.cjs) 只接受旧参数集合。SDK 的直接只读测试可以通过，但真实 managed ToolRuntime 调用 dsha_diagnostics 会在派发前失败；READY 和网页可见不足以证明该调用成功。

SDK 现返回自己的 broker port，允许预期端口参数，并把端口加入连接 generation 摘要。请求前验证预期事实，连接目标始终来自宿主注入的本次 broker；回包前再次核身份。旧调用可省略端口参数，但 generation 仍为必需且包含端口，不能跨端口换代。globalAllow=false、实例/代次核验、独立 broker 凭据和原生确认边界保持。

[定向回归](../../tools/test-recovery-native-consent.mjs)覆盖显式错端口、仅端口变化、旧调用换代拒绝、请求中换端口不重放，以及真实五工具派发与全局/作用域 guard。原先 managed 失败保留，修正后通过并纳入 CI，未跳过该分支。

## 约 400 MiB 体积的根因和修复

Windows 与 Linux 的 pathlib.Path 比较规则不同。[原归档构建器](../../tools/build-dsh-runtime.py)直接 sorted(rglob) 时，同一依赖树产生不同 tar 成员顺序，gzip 摘要不同，使 [应急资产准备器](../../tools/prepare-recovery-assets.py)不能共用正式归档。

本轮对主线锁定归档与 Linux 候选逐成员核验：15,645 个成员（15,005 文件、640 链接），8,530 个 PAX 扩展，成员内容、类型、权限、所有原始头和填充均一致，无增删/重复；仅 11,688 个位置不同。主循环 14,998 项对应 Windows/Posix 的组件排序差异，固定追加的 647 项顺序一致。

构建器改为明确的逐组件小写排序，以原始组件作同键时的确定性次序。不是整条路径字符串排序，也没有删文件、改权限或改应急锁。由真实依赖重新生成后，精确复现主线锁定归档：

- 归档大小：127,308,331 字节。
- SHA-256：`0bf8830eef95e317ffd25d9bce4547871694063d94facbf78104ebe2c197097a`。
- 解压 tar：461,404,160 字节，SHA-256 `fa2976b01a191602c72ff6dc658a5f48ac025c3787d2ce161e4680a268638d10`。

[打包回归](../../tools/test-dsh-runtime-packaging.py)验证实际 tar 次序、逆序遍历仍输出相同 gzip，以及两种 PurePath 的一致性。最终本地 Standard 未签名 APK 为 **292,104,146 字节（278.572 MiB）**；包内应急映射共用正式 DSH 与 Ubuntu 归档，没有额外 recovery-dsh-runtime 归档。独立解压运行根及应急功能保留。

本轮手机安装仍为 14105d4c，没有覆盖安装本次合并结果。最初观察为正式环境的安全启动；随后用户实际启动独立应急，已确认独立 capsule/HOME/profile、proot、guest 与 launcher 出生身份，及独立 Web 与 broker。启动状态 READY，模型凭据未配置。

未发送模型对话、修复提案、确认/写入、备份或停止请求；原始设备图、日志、身份记录和凭据不入 Git。后台冻结的发起者、原生接管记录保存异常、更新 TLS 与账号网络异常仍保持待查，不能声称主线启动保护解决了全部后台管理问题。
